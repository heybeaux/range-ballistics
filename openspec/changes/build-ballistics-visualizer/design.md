# Design

## Context

New local web app. Scout leads and owns quality. Beaux's local Qwen 3.8 model writes the code.
A 27B local model does best with small tasks, fixed interfaces, and tests it cannot argue with, so
the design is built around that.

## Goals / Non-Goals

**Goals**

- Numbers that agree with an independent solver, so the 3D picture can be trusted as far as the
  inputs can.
- A solver that can be tested with no browser.
- An app a new shooter can use without knowing ballistics terms.

**Non-Goals**

- Replacing real dope. The app is a planning aid.
- Powder temperature effects, aerodynamic jump, custom drag curves, several rifles, phone layout.

## Decisions

### Stack: Vite + TypeScript + three.js, no UI framework
Plain TypeScript modules and DOM code. A framework adds concepts the local model must hold in
context and adds nothing this single-screen app needs. Vitest runs the solver tests under Node.

### Layout

```
src/solver/     pure physics: atmosphere, drag, integrate, zero, spin, coriolis, solve, types
src/units/      conversions and formatting (pure)
src/data/       g1.json, g7.json (generated), loads.json (sourced), rifle.json
src/planner/    inputs, results panel, dope table, CSV, print, setup, storage
src/scene/      three.js scene, flags, path, animation, camera
tests/          unit tests, tests/reference/ (independent reference cases)
scripts/        table generator, reference-case generator
```

`src/solver` and `src/units` import nothing from the other folders. The scene and planner read the
solver's output and never compute physics themselves.

### Solver contract (fixed before any code)
Scout writes `src/solver/types.ts` first. Main entry:
`solve(input: ShotInput): SolveResult`, where the result is either an error that names a field, or
`{ zeroAngle, samples[], at(rangeM), transonicRangeM, subsonicRangeM, stability, notes[] }`. Each
sample holds time, position (x downrange, y up, z right, in metres), velocity, and Mach number.
All solver values are SI. The planner converts at the edge.

### Physics

- Frame: x downrange along level ground, y up, z to the shooter's right. For an inclined shot the
  line of sight is rotated about z, gravity stays on y, and drop is measured at right angles to the
  line of sight.
- Drag: `a = (π/8)·ρ·v²·Cd(M)/BC_SI` against the velocity relative to the air.
  `BC_SI = BC × 703.07 kg/m²`.
- Density: dry-air and water-vapour partial pressures. Saturation pressure from the Buck equation.
  Speed of sound `331.3·√(1 + T/273.15)`. Altitude input uses the ISA pressure formula.
- Integrator: RK4, fixed 0.5 ms step, linear interpolation between steps to exact ranges.
- Zero: bisection on bore elevation, level, no wind, in the current atmosphere. A separate "zero
  day" atmosphere is left out. The error at a 100-yard zero is far below one click.
- Spin drift: Miller stability with velocity and atmosphere corrections, then the Litz
  approximation. It is added to the horizontal result after integration. It needs bullet length.
  When the maker does not publish length, the field is blank and the app says spin drift is not
  available until the user measures a bullet.
- Coriolis: `−2Ω×v` inside the integrator, from latitude and direction of fire. Off by default.
- BC note: makers quote BCs against different standard atmospheres (Sierra uses Army Standard
  Metro, most others use ICAO). The difference is about 2%. The app shows this note next to the BC.

### Data that the model must not type
The G1 and G7 tables (79 and 84 points) are generated by `scripts/gen-drag-tables` from the
py-ballisticcalc source, with a checksum test. The load library is filled only from Scout's sourced
research. A local model retyping numbers is the most likely way to get a quiet wrong answer.

### Reference checks that the coder does not write
Scout generates `tests/reference/*.json` with py-ballisticcalc (a separate open-source solver) for
G1 and G7 loads across distance, wind, altitude, and angle. The coder's solver must match within
the tolerance in the spec. The coder cannot change these files.

### Muzzle velocity default
Default = maker's published velocity minus a per-inch loss for the difference between the test
barrel and 16". The per-inch figure and its source are shown in the app. If no sourced figure is
found, the field starts empty and setup asks for a chronograph value or an explicit guess.

### 3D scene
One three.js scene in metres at true scale. OrbitControls for the camera. Flags are simple cloth
strips: yaw from wind direction, lift angle and flutter speed from wind speed. The path is a line
built from solver samples. An exaggeration slider scales y and z offsets from the line of sight
for display only and shows a label when it is not 1×. Animation maps the timeline to solver time.

## Delivery

Each task goes to Qwen 3.8 as one bounded run with: the spec section, the fixed interface, the
files it owns, and the tests to pass. Scout runs the tests, reads the diff, and either merges or
sends it back with the failing case. Order: solver → units → data → planner → scene → setup and
polish → fresh-install walkthrough.

## Risks / Trade-offs

- [Local model writes subtly wrong physics] → independent reference cases, analytic checks, and
  convergence tests that Scout owns.
- [Point-mass model is weak past the transonic range] → the app reports the transonic range and
  warns when the target is past it.
- [Estimated velocity is wrong for a 16" barrel] → labelled as an estimate everywhere until a
  chronograph value replaces it.
- [Local model stalls on a large task] → tasks sized to one module each; Scout splits further if a
  run fails twice.
- [Spin drift formula is an approximation] → shown as an estimate, and can be switched off.
