# Design

## Context

Version 1 holds one rifle and one load list in `AppState`. The solver is already general. The work
is in state shape, data, the form, and the scope view.

## Decisions

### State version 2
`AppState` becomes `{ version: 2, unitSystem, rifles: RifleProfile[], activeRifleId, targetType }`.
A `RifleProfile` holds what version 1 kept at the top level: rifle, scope, load, customLoads,
conditions, dope, spinDrift, setupDone. `loadState` converts version 1 by wrapping it in one
profile. The rest of the planner keeps working on "the active profile", so most modules change by
one line.

### Cartridges are data
`src/data/cartridges.json`: id, name, bullet diameter, velocity-loss figure (Sourced, may be null).
`loads.json` gains `cartridgeId`. Both are generated by script, as now.

### Scope and reticle
`src/data/scopes.json` holds scope profiles. A reticle is a pure function
`reticleShapes(id): Shape[]` returning lines, dots, and text in MRAD (or MOA) units, with tests on
the labelled subtensions. One small drawing module turns shapes into canvas calls at
`pxPerUnit`. Field of view: `fov(mag) = fovAtMin * magMin / mag`, checked against the published
figure at the other end of the range (Venom: 21.2 * 5 / 25 = 4.24 ft against 4.7 published; the
app interpolates between the two published ends instead of assuming exact inverse scaling).

### Delivery
Same method as the first build: the lead writes contracts, data generators, and reference cases;
Qwen writes each module from a bounded brief through the OpenCode CLI; the lead reviews every scene
change in the browser.

## Risks

- [Reticle layout is measured from a drawing] -> labelled on screen; labelled sizes are tested.
- [State migration loses a user's setup] -> migration tests with a real version 1 snapshot.
- [Cartridge data is slow to source] -> add cartridges one at a time; the app works with zero
  library loads for a cartridge.
